Referencia de la **API v1** de JAAK Alnitak. Todos los endpoints de negocio
cuelgan de `/api/v1` y exigen credencial; las sondas y las métricas no.

La URL base es la de tu despliegue: no hay endpoint compartido.

## Autenticación

Tres credenciales, todas aceptadas por el mismo middleware:

| Consumidor | Credencial | Transporte |
|---|---|---|
| Integraciones de servicio | API key de servicio `alnilam_<keyID>_<secreto>` | Cabecera `X-API-Key` |
| Consola de operación (operador humano) | JWT **RS256** emitido tras el SSO | Cookie httpOnly `alnilam_session` o `Authorization: Bearer` |
| Servidor MCP | API key de servicio | Cabecera `X-API-Key` |

De la credencial se resuelven **`tenant`, `canal`, `actor` y `scopes`**, que se
usan para autorización, filtrado por tenant y auditoría.

<Callout type="warning" title="El tenant nunca viaja en la petición">
Tenant y canal se derivan **exclusivamente de la credencial validada**. No se
aceptan como parámetro para autorizar ni para filtrar datos. Enviar un `tenant`
en el cuerpo no cambia nada.
</Callout>

Los fallos de credencial responden `401` o `403` **sin revelar el motivo**: el
mismo mensaje para clave desconocida, mal formada o inválida.

### Scopes

| Scope | Permite |
|---|---|
| `identify` | `POST /api/v1/identify` |
| `enroll` | `POST /api/v1/enroll` |
| `read:metrics` | Métricas, estadísticas de galería, nodos, alertas |
| `read:events` | Eventos recientes, detalle de evento, flujo en vivo |
| `admin:gallery` | Re-embedding y conmutación de alias |
| `admin:erasure` | Supresión de un sujeto de la galería |

## Identificación 1:N

<Endpoint
  method="POST"
  path="/api/v1/identify"
  description="Busca un rostro contra toda la galería y devuelve la lista Top-N con veredicto"
  auth="api-key"
/>

Acepta dos formatos de entrada, con los mismos parámetros en ambos:

| Formato | Cómo va la imagen |
|---|---|
| `multipart/form-data` | En el campo **`image`**, como fichero. Los demás parámetros, como campos del formulario |
| `application/json` | En `image_base64` |

Formatos de imagen aceptados: **JPG y PNG**.

<ParamsTable
  title="Cuerpo (application/json)"
  params={[
    { name: "image_base64", type: "string", required: true, description: "Imagen facial codificada en base64. Tamaño máximo configurable, 4 MiB por defecto." },
    { name: "top_n", type: "integer", required: false, default: "10", description: "Tamaño de la lista de candidatos devuelta. Rango admitido: 1 a 20; fuera de él la petición se rechaza con 400." },
    { name: "num_candidates", type: "integer", required: false, default: "800", description: "Candidatos explorados por shard antes de fusionar. Palanca entre recall y latencia. Máximo 2000." },
    { name: "threshold", type: "number", required: false, default: "0.82", description: "Umbral t del veredicto de tres estados, en escala de coseno normalizado [0,1]." },
    { name: "channel", type: "string", required: false, description: "Canal de origen, para trazabilidad." }
  ]}
/>

### Ejemplo de solicitud

```bash
curl -X POST https://alnitak.interno/api/v1/identify \
  -H "X-API-Key: $ALNITAK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "image_base64": "/9j/4AAQSkZJRgABAQ...",
    "top_n": 5,
    "threshold": 0.82
  }'
```

### Respuesta (200 OK)

```json
{
  "query_id": "q_01J8XK2M4T9F",
  "took_ms": 41,
  "vectorization_ms": 16,
  "threshold": 0.82,
  "top_n": 5,
  "num_candidates": 800,
  "scanned": 4000,
  "quality": { "icao": 0.91, "liveness": 0.97 },
  "candidates": [
    {
      "rank": 1,
      "biometric_id": "bio_8f21c0",
      "record": "EXP-2026-00412",
      "score": 0.913,
      "shard": "3",
      "verdict": "match"
    }
  ],
  "stages": [
    { "name": "Recepción y decodificación", "ms": 0 },
    { "name": "Detección y alineación",     "ms": 12 },
    { "name": "Vectorización",              "ms": 16 },
    { "name": "Búsqueda kNN",               "ms": 9 },
    { "name": "Orquestación",               "ms": 4 }
  ],
  "slack_ms": 359,
  "multi_face": false,
  "model_version": "<modelo-activo>"
}
```

### Campos de la respuesta

| Campo | Qué es |
|---|---|
| `query_id` | Identificador de la consulta. Es la clave para buscarla en la auditoría y en `/events/{id}`. |
| `took_ms` | Tiempo total extremo a extremo, medido con un solo reloj. |
| `vectorization_ms` | Milisegundos de la etapa de vectorización. Es el mismo valor que la etapa `Vectorización` de `stages[]`, expuesto aparte por comodidad. |
| `stages[]` | Milisegundos reales de cada etapa del pipeline en **esta** consulta. Los `name` son los literales en español del servicio (`Recepción y decodificación`, `Detección y alineación`, `Vectorización`, `Búsqueda kNN`, `Orquestación`). |
| `slack_ms` | Diferencia entre un techo configurable del despliegue (`sla.latency_ms`) y el `took_ms` de esta consulta. Útil en operación y métricas; el valor del techo lo define el despliegue. |
| `scanned` | Candidatos efectivamente explorados. |
| `quality` | Puntuaciones ICAO y de vivacidad, en [0, 1]. |
| `candidates[].score` | Similitud coseno **normalizada a [0, 1]**, en la misma escala que `threshold`. |
| `candidates[].verdict` | `match`, `review` o `no_match`. |
| `multi_face` | `true` si la imagen tenía varios rostros: se resolvió con el mayor y la consulta queda marcada. |
| `model_version` | Modelo de vectorización con el que se resolvió. |

La respuesta incluye además un bloque de diagnóstico de la búsqueda —índice
consultado, candidatos totales, score máximo, estado de los shards y la consulta
kNN literal que se envió a Elasticsearch— que la consola usa para trazabilidad.
Se ve renderizado en
[Consola de operación → Consulta kNN](/docs/alnitak/consola#consulta-knn), y
sirve para reproducir una búsqueda fuera del servicio: ver
[Solución de problemas](/docs/alnitak/solucion-de-problemas).

## Alta en galería

<Endpoint
  method="POST"
  path="/api/v1/enroll"
  description="Da de alta una identidad, con control antiduplicado previo"
  auth="api-key"
/>

Mismos formatos de entrada que `/identify`, más el campo `record`.

<ParamsTable
  title="Cuerpo (application/json)"
  params={[
    { name: "image_base64", type: "string", required: true, description: "Imagen facial en base64." },
    { name: "record", type: "string", required: true, description: "Expediente o identificador de negocio que se asocia al rostro." },
    { name: "channel", type: "string", required: false, description: "Canal de origen." },
    { name: "threshold", type: "number", required: false, default: "0.82", description: "Umbral de la comprobación antiduplicado previa." }
  ]}
/>

### Respuesta (201 Created)

```json
{
  "query_id": "q_01J8XK2M4T9F",
  "biometric_id": "bio_8f21c0",
  "record": "EXP-2026-00412",
  "channel": "web",
  "took_ms": 44,
  "vectorization_ms": 18,
  "quality": { "icao": 0.93, "liveness": 0.98 },
  "verdict": "no_match",
  "candidates": [],
  "model_version": "<modelo-activo>"
}
```

El `verdict` de un alta correcta es `no_match`: es el resultado de la búsqueda
1:N previa, y confirma que el rostro no estaba ya en la galería. El `query_id`
es la clave de su evento de auditoría, igual que en `identify`.

<Callout type="danger" title="Un alta con veredicto `review` se GUARDA, no se rechaza">
El rechazo por duplicado se dispara **solo con `match`**. Si la búsqueda 1:N
previa deja el mejor candidato en la banda de revisión —`t ≤ score < t+0.06`—
el alta **se completa con `201`** y el `verdict` de la respuesta es `review`.

No es un error: es el contrato. Pero significa que **tu integración tiene que
mirar el `verdict` de un `201`**, no solo el código de estado. Si tu proceso de
negocio exige revisión humana en esa banda, la decisión de encolar el caso es
tuya: el servicio ya dio de alta el rostro.
</Callout>

<Callout type="info" title="El alta se rechaza también si el modelo no coincide">
El alta se escribe con la versión de modelo que reporta el vectorizador. Si
difiere de la versión activa de la galería, se rechaza: mezclar modelos en el
índice que sirve producción invalida la comparabilidad de los scores. Ver
[Precisión y calibración](/docs/alnitak/precision#cada-cambio-de-modelo-obliga-a-recalibrar).
</Callout>

### Alta rechazada por duplicado (409)

```json
{
  "error": {
    "code": "duplicate_or_fraud",
    "message": "el rostro ya existe en la galería",
    "details": {}
  },
  "candidates": [
    { "rank": 1, "biometric_id": "bio_1a77de", "record": "EXP-2025-00981", "score": 0.958, "shard": "1", "verdict": "match" }
  ]
}
```

Es el único caso en que un error incluye `candidates`: son los que provocaron
el rechazo, para que un operador pueda resolverlo.

## Galería

<Endpoint method="GET" path="/api/v1/gallery/stats" description="Estado del índice: vectores, memoria, shards, parámetros HNSW" auth="api-key" />

```json
{
  "vectors": 50000000,
  "dims": 512,
  "similarity": "dot_product",
  "quantization": "int8",
  "index_ram_bytes": 32212254720,
  "unquantized_ram_bytes": 109951162778,
  "shards": 5,
  "replicas": 2,
  "hnsw": { "m": 16, "ef_construction": 200 },
  "model_version": "<modelo-activo>"
}
```

Requiere `read:metrics`. **Los valores son los del despliegue consultado**, no
constantes del producto: shards, réplicas, similitud y parámetros HNSW se fijan
al crear el índice. Ver
[Galería, vectores e índice](/docs/alnitak/galeria#parámetros-del-índice).

<Endpoint method="POST" path="/api/v1/gallery/reembed" description="Arranca la re-vectorización de la galería con un modelo nuevo" auth="api-key" />
<Endpoint method="GET" path="/api/v1/gallery/reembed/{id}" description="Progreso del trabajo de re-vectorización" auth="api-key" />
<Endpoint method="POST" path="/api/v1/gallery/alias" description="Conmuta el alias de la galería al índice nuevo" auth="api-key" />

Los tres requieren `admin:gallery`. El procedimiento completo, con sus tiempos y
su rollback, está en [Mantenimiento](/docs/alnitak/mantenimiento).

**Arrancar una re-vectorización** — cuerpo de `POST /gallery/reembed`:

```json
{
  "target_index": "galeria_biometrica_v2",
  "source_index": "galeria_biometrica_v1",
  "model_version": "<modelo-nuevo>"
}
```

Solo `target_index` es obligatorio. La respuesta, y la de
`GET /gallery/reembed/{id}`, es el estado del trabajo:

```json
{
  "id": "job_01J8XM...",
  "status": "running",
  "target_index": "galeria_biometrica_v2",
  "source_index": "galeria_biometrica_v1",
  "model_version": "<modelo-nuevo>",
  "processed": 12400000,
  "failed": 3,
  "total": 50000000,
  "vectors_per_sec": 1840.5,
  "started_at": "2026-08-24T02:00:00Z",
  "updated_at": "2026-08-24T04:12:31Z"
}
```

`vectors_per_sec` con `total` es lo que permite estimar cuánto queda: es la
única fuente de tiempo real de la operación. Un trabajo fallido trae `error` y
`completed_at`. **`failed` distinto de cero merece revisión antes de conmutar**:
son rostros que no están en el índice nuevo.

**Conmutar el alias** — cuerpo de `POST /gallery/alias`:

```json
{ "new_index": "galeria_biometrica_v2" }
```

`alias` es opcional; vacío usa el alias de producción. La respuesta confirma
`alias`, `new_index` y `status`.

## Supresión de un sujeto

<Endpoint
  method="DELETE"
  path="/api/v1/biometrics/{id}"
  description="Borra a una persona de la galería: su vector y su recorte cifrado"
  auth="api-key"
/>

Requiere el scope **`admin:erasure`**. Es la operación que atiende un derecho de
supresión: borra **las dos copias** del dato biométrico, el vector del índice y
el recorte cifrado del almacén de objetos.

```bash
curl -X DELETE "$ALNITAK_URL/api/v1/biometrics/bio_8f21c0" \
  -H "X-API-Key: $ALNITAK_ERASURE_KEY"
```

### Respuesta (200 OK)

```json
{
  "biometric_id": "bio_8f21c0",
  "record": "EXP-2026-00412",
  "channel": "web",
  "crop_deleted": true,
  "erased_at": "2026-08-25T09:14:22Z"
}
```

No lleva biometría: cuando esto se serializa, el vector y el recorte ya no
existen. Es lo que el operador necesita para archivar la solicitud que atendió.

| Campo | Qué es |
|---|---|
| `crop_deleted` | Distingue "no había recorte que borrar" de "se borró". Un alta anterior a la custodia de recortes no tiene objeto asociado, y eso **no** es un borrado incompleto |
| `erased_at` | Sello de tiempo UTC del borrado |

<Callout type="danger" title="Es irreversible, y también borra la capacidad de re-vectorizar a esa persona">
No hay deshacer. Y como el recorte cifrado desaparece, **esa persona ya no entra
en una re-vectorización por cambio de modelo**: no queda de dónde reconstruir su
vector. Es el precio de que la supresión sea real — dejar el recorte mantendría
su biometría existiendo.
</Callout>

<Callout type="warning" title="El scope va aparte de `admin:gallery` a propósito">
Reconstruir la galería es reversible: el índice anterior sigue ahí hasta que
alguien lo borra. Suprimir a una persona no lo es. Por eso las dos capacidades
no viajan en la misma credencial, y **ninguna credencial existente hereda
`admin:erasure`**: hay que emitirla explícitamente.
</Callout>

### Errores

| Respuesta | Cuándo |
|---|---|
| `404 not_found` | El `biometric_id` no existe en **tu** galería. **También es la respuesta cuando el documento pertenece a otra organización**: distinguir los dos casos permitiría averiguar si un rostro está enrolado en otra empresa |
| `403 forbidden` | La credencial no tiene `admin:erasure` |
| `500 internal` | El vector se borró y su recorte **no**. La supresión quedó a medias: reintenta la misma llamada, que es idempotente, hasta que devuelva `200` |

<Callout type="danger" title="Un 500 aquí no significa que no pasó nada">
Significa que pasó la mitad. El vector ya no está —la persona no es
identificable— pero el recorte cifrado sigue en el almacén. El mensaje lo dice, y
el reintento lo completa. No lo trates como un fallo sin efecto.
</Callout>

Cada supresión queda en la cadena de auditoría de administración, con el actor,
la organización y el identificador. Cuando el vector y el recorte ya no existen,
**esa fila es la única prueba de que el borrado ocurrió**.

## Métricas y eventos

| Método | Ruta | Scope | Devuelve |
|---|---|---|---|
| `GET` | `/api/v1/metrics/summary` | `read:metrics` | p50, p95, p99, rps, uso de GPU, disponibilidad 30 d, consultas del día y umbrales de latencia/caudal configurados |
| `GET` | `/api/v1/metrics/history` | `read:metrics` | Serie temporal de rps y p95 por bucket |
| `GET` | `/api/v1/metrics/stages` | `read:metrics` | Presupuesto por etapa, total y holgura |
| `GET` | `/api/v1/events/recent` | `read:events` | Últimas consultas atendidas |
| `GET` | `/api/v1/events/{id}` | `read:events` | Detalle de una consulta |
| `GET` | `/api/v1/stream/events` | `read:events` | Flujo en vivo de consultas (SSE) |
| `GET` | `/api/v1/infra/nodes` | `read:metrics` | Carga y estado por nodo del clúster |
| `GET` | `/api/v1/alerts/summary` | `read:metrics` | Alertas del turno |

### `GET /api/v1/metrics/summary`

```json
{
  "p50": 121.0,
  "p95": 204.0,
  "p99": 370.0,
  "rps": 58.4,
  "rps_read": 41.2,
  "rps_write": 17.2,
  "gpu_use": 0.62,
  "availability_30d": 0.9993,
  "downtime_minutes_30d": 30.2,
  "observed_since": "2026-07-01T00:00:00Z",
  "queries_today": 184320,
  "sla": { "latency_ms": 400, "rps": 60 }
}
```

`gpu_use`, `availability_30d` y `downtime_minutes_30d` son **`null`** mientras no
haya ventana suficiente de observación; `observed_since` marca el inicio de la
ventana. El bloque `sla` devuelve el techo declarado del despliegue, no una
garantía del servicio: ver
[Configuración → Techo de latencia](/docs/alnitak/configuracion#techo-de-latencia-declarado).

### `GET /api/v1/metrics/history`

Array de buckets:

```json
[
  { "ts": "2026-08-24T10:00:00Z", "rps": 58.4, "rps_read": 41.2, "rps_write": 17.2, "p95": 204.0 }
]
```

### `GET /api/v1/metrics/stages`

```json
{
  "stages": [
    { "name": "Recepción y decodificación", "ms": 0 },
    { "name": "Detección y alineación",     "ms": 13 },
    { "name": "Vectorización",              "ms": 5 },
    { "name": "Búsqueda kNN",               "ms": 10 },
    { "name": "Orquestación",               "ms": 3 }
  ],
  "total_ms": 31,
  "slack_ms": 369,
  "budget_ms": 400
}
```

Es el reparto **agregado** de la ventana reciente. `budget_ms` es
`sla.latency_ms`, y `slack_ms` la holgura contra él.

### `GET /api/v1/events/recent` y `GET /api/v1/stream/events`

Filas resumidas, en el mismo formato en los dos casos. `stream/events` las
entrega como **Server-Sent Events** (`text/event-stream`), una por mensaje:

```json
{
  "id": "q_01J8XK2M4T9F",
  "ts": "2026-08-24T10:14:22Z",
  "channel": "web",
  "top1_score": 0.913,
  "ms": 41,
  "verdict": "match"
}
```

El `id` es el `query_id` de la consulta.

### `GET /api/v1/events/{id}`

```json
{
  "id": "q_01J8XK2M4T9F",
  "ts": "2026-08-24T10:14:22Z",
  "channel": "web",
  "quality": { "icao": 0.91, "liveness": 0.97 },
  "num_candidates": 800,
  "top_n": 5,
  "shards": { "queried": 5, "total": 5 },
  "verdict": "match",
  "candidates": [
    { "rank": 1, "biometric_id": "bio_8f21c0", "score": 0.913 }
  ]
}
```

<Callout type="warning" title="El detalle de evento NO trae el desglose por etapa">
`stages[]` **solo viene en la respuesta del `identify` original**. Este endpoint
devuelve calidad, parámetros de búsqueda, shards consultados, veredicto y
candidatos, pero no los milisegundos por etapa.

Consecuencia práctica: si quieres diagnosticar *a posteriori* dónde se fue el
tiempo de una consulta concreta, **hay que haber guardado el `stages[]` de la
respuesta en el momento**. Para el reparto agregado, usa `/metrics/stages`.
</Callout>

### `GET /api/v1/infra/nodes`

```json
[
  { "name": "es-data-0", "role": "data", "cpu_load": 0.41, "state": "green" }
]
```

### `GET /api/v1/alerts/summary`

```json
{
  "identity_theft": 0,
  "duplicate_enrollment": 3,
  "low_quality": 17,
  "shift_start": "2026-08-24T06:00:00Z"
}
```

Son contadores **del turno**, desde `shift_start`. Qué significa cada uno y qué
hacer con él, en [Operación → Alertas del turno](/docs/alnitak/operacion#alertas-del-turno).

## Sondas y métricas de plataforma

| Método | Ruta | Auth | Para qué |
|---|---|---|---|
| `GET` | `/healthz` | No | Liveness: el proceso está vivo |
| `GET` | `/readyz` | No | Readiness: listo para atender tráfico |
| `GET` | `/metrics` | No | Métricas en formato Prometheus |

Ninguna expone configuración, credenciales ni detalles internos.

### `GET /healthz`

```json
{ "status": "ok" }
```

Solo dice que el proceso responde. **No comprueba ninguna dependencia**, así que
un `healthz` en verde con el servicio inservible es un estado posible y esperado.

### `GET /readyz`

Listo — `200`:

```json
{
  "status": "ready",
  "checks": { "elasticsearch": true, "vectorizer": true }
}
```

No listo — `503`:

```json
{
  "status": "not_ready",
  "message": "vectorizador: context deadline exceeded",
  "checks": { "elasticsearch": true, "vectorizer": false }
}
```

El bloque `checks` es lo que hace útil esta sonda: **divide el problema en dos
antes de que empieces a buscar**. El `message` trae la causa concreta.

<Callout type="warning" title="`gallery_blocked`: Elasticsearch responde y la galería no está montada">
La respuesta puede incluir además `"gallery_blocked": true`. Significa que
Elasticsearch contesta con normalidad **pero un índice plano ocupa el nombre del
alias de producción**, así que el esquema versionado no se puede montar.

No se sale de ese estado reiniciando: hay que
[migrar el índice](/docs/alnitak/mantenimiento#migrar-un-índice-plano-preexistente).
</Callout>

## Formato de error

Todos los errores comparten el mismo sobre:

```json
{
  "error": {
    "code": "low_quality",
    "message": "la imagen no supera el umbral de calidad",
    "details": {}
  }
}
```

| Código | HTTP | Causa | Qué hacer |
|---|---|---|---|
| `invalid_image` | `400` | Formato no soportado (solo **JPG y PNG**), imagen corrupta, por encima del tamaño máximo, o `top_n`/`num_candidates` fuera de rango | Revisar formato, tamaño y parámetros antes de enviar |
| `low_quality` | `422` | Sin rostro detectable, o calidad/vivacidad por debajo del umbral | Recapturar con mejor iluminación y encuadre |
| `unauthorized` | `401` | Credencial ausente, desconocida, mal formada o inválida | Revisar la credencial |
| `forbidden` | `403` | Credencial válida sin el scope requerido | Solicitar el scope |
| `not_found` | `404` | Recurso inexistente | — |
| `duplicate_or_fraud` | `409` | El rostro ya está en la galería (solo en alta) | Resolver el expediente duplicado |
| `rate_limited` | `429` | Superado el límite por IP y ventana | Reducir la tasa, o revisar `trusted_proxies` |
| `vectorizer_unavailable` | `503` | El motor de tokenización no responde | Revisar el vectorizador y las GPU |
| `gallery_unavailable` | `503` | Elasticsearch no responde | Revisar el clúster de la galería |
| `internal` | `500` | Error no clasificado | Revisar logs con el `query_id` |

<Callout type="warning" title="429 antes de tiempo">
Un `429` con el servicio lejos de su capacidad puede indicar que el tráfico
entra por un gateway y comparte la cuota de una sola IP. Revise primero la
configuración del limitador antes de atribuirlo a saturación: se corrige
declarando el gateway en `server.trusted_proxies`, ver
[Configuración → Limitador de peticiones](/docs/alnitak/configuracion#limitador-de-peticiones).
</Callout>
